# Kettle

Everyday AI video courses in Hindi for Indians over 40. Mobile-first PWA. One Next.js app, MongoDB on Atlas, deployed on Render. Solo engineer, so every choice favors one person being able to run it.

## Rules that are not obvious from the code

- **Viewer state is the spine.** `src/lib/viewer.ts` resolves `anonymous | free | gold` plus the tenant once per request. Every gating decision, popup, and nav item is a function of it. No page decides access on its own.
- **Every tenant-scoped query goes through `withTenant()`.** `src/lib/db/scope.ts` hands you a handle that narrows every read and stamps every write with the tenant; `src/lib/db/collections.ts` classifies each collection. Never take a tenant id from the client. `bypass` is for the seed script and the payment webhook only.
- **Nothing outside `src/lib/db` imports the MongoDB driver.** This is the rule that replaced row-level security, and it is now the whole of the isolation guarantee. Postgres refused another tenant's rows itself, so a forgotten filter returned nothing; MongoDB returns everything. `npm run check:tenancy` proves the scoped path holds, but it cannot see a raw driver call made elsewhere — hence the rule.
- **Row-level security is FORCEd**, so it applies to the table owner too. A missing `set_config` returns zero rows rather than all rows. If a page shows nothing unexpectedly, that is usually why.
- **Every route handler** parses input with a schema from `src/lib/security/validators.ts`, checks `assertSameOrigin` on mutations, and rate limits with `src/lib/security/rate-limit.ts`. Webhooks skip origin checks and verify a signature instead.
- **Admins are a list of phone numbers in `ADMIN_PHONES`, never a column.** `src/lib/admin.ts` is the whole of it. A role flag in the database would mean anyone who reached the Atlas cluster — which holds another app's data behind a weak password — could publish a lesson pointing at any video they liked, to an audience taught to trust this product. An environment variable cannot be written from inside the app. Unset means nobody, which is right for every environment that is not Rishav's. Every `/api/admin` route calls `adminPreamble` first: origin, then identity, then rate limit, then body.
- **A guard in a layout does not stop a page's data.** This one cost a real leak. A layout and its page render in parallel, so `notFound()` in `src/app/admin/layout.tsx` swapped the visible UI while `page.tsx` had already run its query — and the entire catalogue, unpublished drafts included, went out inside the 404's own RSC payload. Every page under `/admin` therefore calls `getAdmin()` and refuses **before** it fetches. The layout guard stays as a second line, not the only one. `npm run smoke` asserts no course title comes back with that 404.
- **`--violet` is Pine, `#00311f`.** It is the accent name inherited from the design this started as, and it is near-black. Anything that stacks it — a border plus a ring — draws two concentric black lines and reads as a box pasted over the element. Focus states use a single `ring-violet/35`.
- **Pine on white.** Text and controls are Pine `#00311F`; the ground is white. Milk `#F0EEE6` is a secondary surface only. Every grey is a tint of pine. Components use the semantic tokens in `globals.css` (`ink`, `paper`, `fill`, `line`, `wash`), never raw hex. No gradients — with one exception, `.gold-surface`. Large blocks are outlined, not filled; only controls (buttons, tabs, avatars, step numbers) are solid pine.
- **Night mode is opt-in only.** The Night chip sets `data-theme="dark"`. The stylesheet deliberately does not follow `prefers-color-scheme`, because a dark screen in daylight on a cheap phone is the wrong default for this audience. Do not add the media query back.
- **Devanagari leading.** Hindi never renders below `line-height: 1.34` for headings or `1.5` for body. Use the `.dv` class or `lang="hi"`. Latin leading crushes matras.
- **Bilingual copy uses `<T hi en />`** from `src/components/bilingual.tsx`. It renders both languages and switches on `<html lang>` with CSS, so it works in server components with no flash and needs no language passed in. `<TN>` is the same for copy containing elements — a sentence with a link in it, where the link sits in a different place in each language.
- **An attribute cannot be hidden by language, so it has to choose.** `pick(lang, hi, en)` from `src/lib/pick.ts` is for placeholder, aria-label and alt. Server components get `lang` from `getLang()`; client components get it from `useLang()`, provided once in the root layout. **`pick` lives in `src/lib/pick.ts` and nowhere else**: it started life in the client module beside `useLang`, where every server caller type-checked, built, and then threw "Attempted to call pick() from the server" at request time. Neither `tsc` nor `next build` catches that.
- **The hero demo is the one exception.** It types its question a character at a time, so the text is state rather than markup and CSS cannot hide the other language. It picks a script up front in `src/components/hero-typing-demo.tsx`.
- **The policy pages are bilingual too, and say which version governs.** A translated policy with no rule for disagreement is worse than none. `Governing` in `src/app/legal/parts.tsx` carries that line; both versions still need the same legal review, and every TO CONFIRM is still outstanding.
- **Page metadata stays English.** Titles and descriptions are for search engines and browser tabs, and are not switched.
- **The domain is `getkettleai.com`, and the hero must not contradict it.** `NEXT_PUBLIC_SITE_URL` drives every canonical URL, OG tag and sitemap entry, and is set on Render. The hero demo draws a mock browser with an address bar, and that address is the one thing on the landing page a reader is invited to read as a real address, so `siteHost()` in `src/lib/seo.ts` derives it from the same variable. It was previously the literal `kettle.ai` — a domain this product does not own, shown to an audience whose first course teaches them to read the address bar before trusting what is under it.
- **Video audio is Hinglish, text comes in two full tracks.** One shoot per lesson, no English re-record. The `*Hi` fields are written in that same spoken register: Devanagari with English loanwords left in Latin, as in "Resume बनाइए". The `*En` fields are plain English. So mixed-script lines are normal here, not an exception, which is why the type is Anek: both faces load Devanagari and Latin, so one line renders in one family instead of colliding two. Captions must be written by hand; automatic captioning fails on code-switched speech.
- **Type floor.** Body text is 17px on phones, 20px with `data-textsize="big"`. Tap targets never drop below 44px.
- **The stage is the shape of the video, not always 16:9.** These are filmed on a phone held upright, so `video_assets.orientation` is usually `portrait` and `stageClass` in `src/lib/video/embed.ts` sizes the frame from it — portrait bounded by height, landscape by width, which is the constraint each actually has. A 9:16 video in a 16:9 box is a thin strip with black down both sides using about a third of the space. Assets written before the field default to landscape; the editor has a Shape control next to every video link, and `npm run db:orientation` fixes a batch.
- **Lessons never store a YouTube ID.** They reference `video_assets`; `src/lib/video/embed.ts` is the only place that knows about providers. A ref starting with `TODO` renders as "video being added".
- **Exactly four lessons are free.** The seed script refuses any other count, and `/api/admin/lessons` refuses a fifth.
- **Two levels: category, then lesson. There are no courses.** They were removed on 2026-09-21 because in eight of the eleven filled categories there was exactly one course, so the layer was a tap to a page repeating the category under a near-identical name — in "Start with AI" it was the same name exactly. `isPublished` and the card image moved down to the lesson; the description moved up to the category. `scripts/flatten-courses.ts` did the migration and can be deleted once every database has been through it. Lesson ids were never touched, so progress and the free-watch log survived. `/courses/*` 308s to `/learn` in `next.config.ts`.
- **A lesson's card art is its YouTube thumbnail.** A frame of the actual lesson, free, and never stale. `imageUrl` on the lesson is the override and the fallback while a video is still TODO.
- **Social proof must be real — with one declared exception.** The joiners popup reads from actual memberships and names actual people; testimonials and the teacher block come from `content/kettle-site.json` and render with an EXAMPLE chip until they are real. Never fabricate a signup or a testimonial. The audience is scam-targeted and the product teaches scam avoidance.
- **Gold is a material, not a colour.** `.gold-surface` in `globals.css` is the only gradient in the product: a 135deg sweep from `--gold-edge` bronze through `--gold` to a `--gold-lit` champagne band and back, with a bright inset hairline on top and a dark one beneath. A single flat fill can only ever read as ochre, which is what `#c9a227` did. It is fixed — no animated shimmer, because the first course teaches this audience to distrust a page that glitters at them. `--gold-wash` and `--gold-line` warm the ground around it so the panel is not a gold rectangle stapled to a white page. **Contrast was measured, not eyeballed**: `--on-gold` against `--gold-edge`, the darkest stop, is 5.0:1. Darkening the edges or lightening the ink breaks AA for body text on the one screen that asks for money.
- **A horizontal shelf needs `scroll-px-*` matching its gutter.** `scroll-snap-type: x mandatory` sits on a valid snap point at load, and with no scroll-padding the snapport starts at the padding-box edge — so an overflowing shelf scrolled its own left gutter out of view while a shelf of one card kept it. The symptom looks like a padding bug that depends on how many cards there are.
- **The exception is `FLOOR` in `src/components/landing.tsx`.** Rishav set the landing strip's learner, lesson and minute figures as floors on 2026-09-14, so those three are asserted rather than counted: the floor shows with a `+` until the real number passes it, then the real number takes over. This is a deliberate decision, not a bug — do not "fix" it back to counting. It is also the only place in the product where a displayed number is not measured, and it should stay that way. The free-lesson tile carries no `+`, because exactly four lessons are free and `4+` could never become true.
- **The business details live once, in `content/kettle-site.json` under `business`.** Entity name, registered address, telephone, email, grievance officer, jurisdiction and the last-updated date. All four policy pages render from that block, because these facts used to be typed into each page separately and a payment reviewer compares them. While `placeholder` is true every one renders outlined with an EXAMPLE chip, so a half-filled policy page is visible on the page rather than only in a grep. `npm run check:legal` lists what is still unfilled and why Razorpay wants it.
- **Unfilled landing content is flagged, not faked.** `content/kettle-site.json` holds the teacher, testimonials and FAQ. Any entry with `"placeholder": true` renders with a dashed border and an EXAMPLE chip so it cannot ship unnoticed. Replace with real people and real photographs, then drop the flag.
- **No urgency, ever.** No countdown, no "offer ends", no struck-through price. Most comparable products do this; it is the visual grammar of the scams our first course warns about.
- **Entitlement flips only from the server.** Payment success is confirmed by the Razorpay webhook writing to `memberships`. The client polls `/api/payments/status`, it never asserts. `/api/payments/simulate` stands in for the webhook locally and refuses to exist in production.
- **Which Razorpay keys a process uses is derived, never chosen.** `src/lib/payments/keys.ts` picks by `NODE_ENV`: production takes `RAZORPAY_LIVE_*`, everything else takes `RAZORPAY_TEST_*`, and the undecorated `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` pair still works for a deployment carrying only one set. The part that matters is the refusal — a live key outside production disables payments entirely and logs why, because both sets live in the same `.env.local` and the only thing separating a smoke run from real charges was remembering. Each mode has its own webhook secret, since Razorpay issues one per webhook and the test and live dashboards are separate. Nothing outside that file reads a Razorpay variable: `createOrder` returning `env.RAZORPAY_KEY_ID` was how checkout came to be handed a null key id under the split names.
- **Both naming forms set to different values is refused, not resolved.** The undecorated `RAZORPAY_*` names win over the decorated ones, because they must for deployments predating the split. That makes a leftover `RAZORPAY_WEBHOOK_SECRET` from an earlier Razorpay account silently beat the `RAZORPAY_LIVE_WEBHOOK_SECRET` someone just set, with nothing visible to show for it — the key id in the boot log can look right while the webhook secret is the stale one, so the payment succeeds at Razorpay, the callback fails verification, and the charge is real with no membership behind it. `keys.ts` therefore refuses to resolve at all and names both variables. Identical values are allowed, since that is one variable written twice rather than two answers.
- **Test mode on the deployed site is possible, declared, and dated.** `RAZORPAY_TEST_MODE_UNTIL` is a date; while it is in the future, production resolves to the test keys, so the paid flow can be walked on the real domain with the real webhook. It exists because a webhook needs a public URL and the only one this product has is the deployed site, so the alternative is tunnelling to a laptop and testing a machine no customer will use. It is a date rather than a flag because the failure it invites is forgetting: a site on test keys takes no money and looks like it is working, which is the quietest way to lose every sale. It expires on its own and warns loudly at boot, the same shape as `REVIEW_UNTIL`. The refusal in `keys.ts` is unchanged — it stops an accident, not a declared choice.
- **`simulate` gates on production, not on whether keys exist.** It used to refuse the moment any key was configured, which meant configuring Razorpay for testing switched off the one path `npm run smoke` uses to get past the paywall. Test keys move play money; the machine holding them is exactly where the stand-in is wanted. It does not check whether live keys are merely present either, because they sit in `.env.local` beside the test pair where `keys.ts` already refuses to use them.
- **The review account is the one fixed credential, and it is deliberately narrow.** `src/lib/auth/review.ts`. Razorpay will not approve a website without testing checkout and their form asks for a password, which this product does not have. The nominated phone goes through the entire ordinary path — challenge row, expiry, attempt cap, both rate limits, constant-time compare — and exactly two things differ: the code is fixed rather than random, and no SMS is sent. It refuses to work if the number is also in `ADMIN_PHONES`, `REVIEW_UNTIL` expires it on its own, and it warns loudly at boot. `npm run smoke:review` proves the narrowness, not just that it works.
- **Sessions are documents, not signed tokens.** The cookie holds an opaque secret; the database holds only its SHA-256 hash. That makes revocation and account deletion real. `src/lib/auth/session.ts` is one of the few places that touches the database outside `withTenant()`, because the tenant is not known until the session is read.
- **Secrets resolve on use, not on import.** `getAuthSecret()` and the SMS sender are lazy, because `next build` evaluates every route with `NODE_ENV=production` before secrets are necessarily in scope. A module-level throw breaks the build; a lazy one still refuses a real request.
- **Swapping the SMS provider is one file.** `src/lib/auth/sms.ts` holds the interface, the dev sender that prints to the log, and the MSG91 implementation. India needs DLT registration per template per language.
- **`DATABASE_URL` is required everywhere, including locally.** MongoDB has no in-process equivalent of the embedded Postgres this used to run, so there is no zero-setup path any more: a clean checkout needs an Atlas connection string before `npm run dev` will serve a page. It must name a database, or the driver quietly uses one called `test`.

## Layout

- `src/app` routes. `/kit` is the component kit, not linked from the product. `/admin` is the catalogue editor: English only, because it is the operator's tool and the operator is one person — the content typed into it is bilingual, which is the part that matters.
- `src/components/ui` the reusable pieces. `src/components/app-shell.tsx` is the frame every signed-in screen uses: one column with a bottom bar on phones, a fixed sidebar and a content area from `lg` (1024px) up. Pass `width="wide"` for catalog-style pages, the default `"reading"` for everything else.
- **Two layouts, one tree.** Phone first, then `lg:` overrides. Never a separate desktop route or component. A phone column centred in a desktop window reads as unfinished, so from `lg` the landing page goes two-column and the app grows a sidebar.
- `src/lib/db/documents.ts` the whole data model as document types. `src/lib/db/indexes.ts` is what replaced the migrations: applied on every connection, it carries the uniqueness constraints the app's correctness depends on — one phone to one account, one receipt to one charge, one progress document per lesson.
- **The database is the catalogue's source of truth; `content/kettle-content.json` is the bootstrap.** Since /admin can write content, `npm run db:seed` refuses against a database that already holds lessons and needs `-- --force` to overwrite. The file remains the fixture a clean checkout starts from. `content/kettle-site.json` is the landing page content and is read at request time, no seed needed.
- **`src/lib/content/queries.ts` is the learner's view of the catalogue; `admin-queries.ts` is the editor's.** They are deliberately separate: the first hides unpublished lessons and knows nothing about TODO video refs, the second exists to show exactly those. One query serving both ends up hiding work from one reader or leaking drafts to the other.
- `src/components/landing.tsx` holds the landing sections; `src/app/page.tsx` is mostly the ordering decision, which is the part that matters. The order follows verified patterns from thirteen comparable products, with two departures noted in the file.
- `src/components/logo.tsx` is the kettle mark, inline so it inherits `currentColor`. `scripts/make-demo-art.mjs` regenerates the placeholder course and portrait art; delete it when real photographs land.

## Commands

```
npm run dev          # needs DATABASE_URL; indexes are applied on connect
npm run db:seed      # load content/kettle-content.json
npm run db:ping      # prove the cluster is reachable, without printing secrets
npm run build        # what Vercel runs
npm run typecheck && npm run lint
npm run check:tenancy # proves tenant isolation through the scoped handle
npm run check:legal   # what is still unfilled before Razorpay will approve a live account
npm run smoke:review -- http://localhost:3080   # the reviewer sign-in; needs REVIEW_* set on the dev server
npm run smoke:payments -- http://localhost:3080 <path-to-dev-log>   # a real test-mode order plus a webhook signed the way Razorpay signs one
npm run smoke -- http://localhost:3080 <path-to-dev-log>   # walks the whole product
npm run smoke:admin -- http://localhost:3080 <path-to-dev-log>   # drives /admin; needs ADMIN_PHONES set on the dev server
npm run db:flatten              # one-time: category > course > lesson becomes category > lesson (dry run; --write to apply)
```

## Verifying

`scripts/check-rls.ts` proves a query with no tenant set sees nothing, that one tenant cannot read or write another's rows, and that global content stays visible. `scripts/smoke.mjs` drives a running server the way a browser would, with a cookie jar and real origin headers: it signs in with the code from the dev log, onboards, completes the four free lessons, checks the fifth is refused, pays through the simulated webhook, and confirms the lock lifts. It also probes what must fail, including a forged webhook signature, a cross-origin write, and every route into the catalogue editor from an ordinary signed-in learner.

`scripts/smoke-admin.mjs` is the other half of that: it signs in as an admin and proves the editor works — a category, a course and a lesson created, a messy watch URL stored as a bare id, a fifth free lesson refused, a category with courses refused, a draft absent from Learn until published — then deletes everything it made. It needs a dev server started with `ADMIN_PHONES` containing its test number, so it is a separate command. `scripts/smoke-payments.ts` covers the half of the paid path that `smoke` cannot reach. `smoke` settles through the stand-in, which proves everything downstream of the webhook and nothing upstream of it: not that an order can actually be created at Razorpay, and not that a real signature verifies. Those two are where the money is. It needs no tunnel and no public URL, because the signature is the whole of the proof and can be produced locally — so the webhook secret it signs with only has to match the server's, not Razorpay's. It refuses to run outside test mode.

Run `smoke` and `check:tenancy` before any deploy, `smoke:admin` after touching anything under `/admin`, and `smoke:payments` after touching anything under `src/lib/payments`.
